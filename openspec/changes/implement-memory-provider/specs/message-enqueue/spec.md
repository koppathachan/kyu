## ADDED Requirements

### Requirement: Messages are stored with their full content
`SaveMessage` SHALL store the payload bytes, the string-to-string attributes, and the signed 32-bit priority, and SHALL return a provider-generated `message_id` together with the `saved_at` timestamp on the provider's clock. An empty payload SHALL be legal.

#### Scenario: A saved message round-trips on delivery
- **WHEN** a message is saved with a payload and attributes, and later leased
- **THEN** the leased message carries the same `message_id`, `queue_id`, payload bytes and attributes

#### Scenario: An empty payload is accepted
- **WHEN** `SaveMessage` is called with a zero-length payload
- **THEN** the save succeeds and the message becomes leasable

### Requirement: Message identifiers are opaque and time-ordered
`message_id` SHALL be an opaque string of at most 128 characters, generated by the provider, and SHALL sort lexicographically in creation order so that it serves as the final ordering tiebreak of §3.2.

#### Scenario: Ids sort in creation order
- **WHEN** several messages are saved in sequence
- **THEN** their `message_id` values compare in the same order as they were saved

### Requirement: Visibility delay defers first delivery
When `visibility_delay` is present, the message SHALL become visible at save time plus that duration, and SHALL NOT be leasable before then. A delay SHALL NOT count as a delivery. When `visibility_delay` is absent the message SHALL be visible immediately.

#### Scenario: A delayed message is not immediately leasable
- **WHEN** a message is saved with a visibility delay and a lease is attempted straight away
- **THEN** no message is returned

#### Scenario: A delayed message appears after its delay
- **WHEN** the visibility delay has elapsed
- **THEN** the message is leasable, and its `delivery_count` on that first delivery is 1

### Requirement: Deduplication by idempotency key
When `idempotency_key` is non-empty, a save whose `(queue_id, idempotency_key)` pair matches a deduplication record still inside the queue's `dedup_window` SHALL return the **original** `message_id` with `deduplicated = true` and SHALL NOT store a second message. When `idempotency_key` is empty no deduplication SHALL occur.

#### Scenario: A duplicate inside the window
- **WHEN** the same `(queue_id, idempotency_key)` is saved twice inside the window
- **THEN** the second response carries the first response's `message_id`, has `deduplicated = true`, and the queue holds exactly one message

#### Scenario: A different key is a different message
- **WHEN** two saves use different idempotency keys in the same queue
- **THEN** two distinct messages are stored and neither is flagged `deduplicated`

#### Scenario: No key means no deduplication
- **WHEN** two identical saves omit `idempotency_key`
- **THEN** two distinct messages are stored

### Requirement: The deduplication window is measured from the original save
The deduplication window SHALL be measured from the time the original message was saved, not from the most recent duplicate attempt. After the window has elapsed, the same key SHALL produce a new message and a new deduplication record.

#### Scenario: After the window a new message is created
- **WHEN** a key is saved, the queue's `dedup_window` elapses, and the same key is saved again
- **THEN** the second save returns a new `message_id` with `deduplicated = false`

### Requirement: Deduplication records outlive their messages
A deduplication record SHALL be independent of the fate of the message it names. A duplicate save inside the window SHALL still return the original `message_id` with `deduplicated = true` even after that message has been acked, deleted or dead-lettered.

#### Scenario: A duplicate after the original was acked
- **WHEN** a keyed message is saved, leased and acked, and the same key is saved again inside the window
- **THEN** the response carries the original `message_id` with `deduplicated = true`, and the queue still holds no messages
